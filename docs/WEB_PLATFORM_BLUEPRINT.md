# المخطط الهندسي الشامل — ديوان الحازمي (Next.js / TypeScript)

> الحالة: مخطط تنفيذ معتمد للتطوير، لا يعني أن واجهة الموقع أو خدمات API قد نُفذت. تاريخ الإعداد: 2026-11-15.
> المشروع منصة أهلية خاصة بالقبيلة، وليس جهة حكومية أو سجلًا مدنيًا.
> المصادر الأساسية: `docs/PROJECT_PLAN.md`, `docs/DATA_MODEL.md`, `docs/SECURITY.md`, `docs/DELIVERY_STATUS.md` ومهاجرات SQL القائمة.

## 1) نتائج التدقيق والمبادئ الملزمة
- المستودع `youef/alhazmi` يحوي بالفعل ملفات SQL ووثائق واختبارات، ولا يحوي تطبيق Next.js بعد.
- يذكر `docs/DELIVERY_STATUS.md` وجود Neon PostgreSQL 17 مع 119 جدولًا و335 مفتاحًا خارجيًا وترحيلات V1–V10؛ هذه أرقام **بحسب التقرير الموجود بالمستودع** وليست نتيجة فحص مباشر حالي لقاعدة الإنتاج.
- بيانات وحدات النسب المستوردة من المصادر التاريخية **قيد المراجعة**؛ ليست سجلات أنساب موثقة، ولا تُنشر كحقائق نهائية.
- الحفاظ على الجداول والمهاجرات السابقة، وعدم حذف أو إعادة تسمية أي عمود قبل جرد التوافق وترحيل تدريجي آمن.
- كل سلوك أمني على الخادم وقاعدة البيانات؛ واجهة React ليست حدود ثقة.
- الأمن الافتراضي: الرفض، أقل صلاحية، سجل تدقيق، عدم كشف بيانات القاصرين والأحياء، فصل التوثيق والتكافل عن النسب العام.
- لا أسماء أشخاص حقيقيين ولا هويات ولا وثائق ولا مفاتيح في GitHub.

## 2) الرؤية والمنتج
الجمهور: زائر عام، عضو موثق، ممثل عائلة، مشرف فخذ، نسّابة ومراجع مصادر، مسؤول أرشيف، مسؤول مناسبات، مسؤول تكافل، مدقق، مدير أعلى. الهدف قاعدة أنساب تاريخية قابلة للتدقيق، ملفات أسرية اختيارية، خدمة طلبات التصحيح، ذاكرة تراثية، وإدارة آمنة.

### أدوار الاستخدام
1. الزائر يطالع الأخبار والمحتوى المنشور والوحدات التاريخية المعتمدة فقط.
2. العضو يسجل حسابًا ويطلب ربطه بسجل شخص، ويتابع طلباته ويتحكم بخصوصية بياناته.
3. مشرف الأسرة يرى الطلبات المسندة إلى نطاقه دون اطلاع تلقائي على هويات حساسة.
4. النسابة يراجع أدلة العلاقة ويعتمد/يرفض بحسب سير الموافقات والصلاحيات.
5. مدير الوثائق يدير ملفات خاصة وآجال الاحتفاظ دون منح صلاحية تعديل النسب.
6. الإدارة تراقب الجودة والقرارات والسجلات، وصلاحياتها الدقيقة لا تُستنتج من عنوان الدور.

## 3) المتطلبات الوظيفية الكاملة
- دليل القبيلة: قبيلة > بطون/فروع > أفخاذ > عوائل > بيوت حسب البنية المرنة الحالية، مع الأسماء التاريخية والمتغيرات والهجرات ودرجة الاعتماد.
- سجل الشخص: معرف ثابت، اسم عربي مفصل، بدائل الأسماء، أسماء الأب والأم المعتمدة، الميلاد/الوفاة إن توافرت بأشكال تاريخ دقيقة/تقريبية، بيانات أهلية منفصلة.
- شجرة النسب: خطوط أب وأم واضحة، آباء/أمهات وأجداد وأحفاد، طي/توسيع وتجميع وخرائط للأجيال، مؤشر الثقة ومصادر الأدلة، تقييد نطاق الطلب.
- روابط الزواج والمصاهرة والرعاية/الولاية والكفالة تسجّل مستقلة عن روابط الأبوة ولا تُنتج أبناء تلقائيًا.
- البحث: تطبيع الحروف العربية، إزالة التشكيل عند الفهرسة، أسماء بديلة، فصل المتشابهين، اقتراحات مصحوبة بحالة التوثيق والخصوصية.
- حاسبة القرابة: طريق بين شخصين مصرح بمشاهدتهما، وصف عربي للمسار، تنبيه نقص البيانات والتنازع؛ الخوارزمية لا تدّعي نتيجة يقينية لمسار غير موثق.
- الخدمات الذاتية: طلب إضافة شخص، تعديل اسم، توثيق أبوة، طلب إضافة عائلة، تعديل علاقة، الإبلاغ عن خطأ، ربط الحساب، حذف/تقييد بيانات حسب السياسة.
- الأرشيف: صور ووثائق ومخطوطات ومقابلات ومصادر، حقوق استخدام، مراجعة، نسخ وإصدارات وفهرسة، روابط تنزيل قصيرة الصلاحية.
- أخبار وأحداث ومناسبات، ملفات شخصيات بارزة بموافقة، إدارة التكافل بمحاسبة وتفويض مستقلين.
- تحليلات إجمالية مع إخفاء المجموعات الصغيرة وحماية الإحصاءات من كشف الأفراد.
- لوحة مسؤول: طلبات، أفراد، وحدات، محتوى، مصادر، أدوار وصلاحيات، سجلات تدقيق، إعدادات الخصوصية والجودة، حالة المهام والاستيراد.
- الموقع يعمل على الهاتف أولًا، RTL وLTR بحسب اللغة، وضع ليلي، وصولية ولوحة مفاتيح، وطباعة/تصدير مصرح به.

## 5) نموذج البيانات وكتالوج المجالات
**ملاحظة:** أسماء الجدول التالية تربط إلى ما ورد في `docs/DATA_MODEL.md`، ويجب توليد قاموس حقول وفهارس آليًا من `information_schema` بعد الاتصال الفعلي، لا افتراض تطابق 119 جدولًا دون جرد.

| المجال | كيانات أساسية | العلاقة والقيد |
|---|---|---|
| الوحدات | tribes, lineage_units | parent_id هرمي مع منع التداخل الدوري |
| الأشخاص | people, person_private | معرف ثابت، بيانات خاصة معزولة |
| الأسماء | أجزاء الاسم والبدائل التاريخية | لا تُخلط هوية شخصين لتشابه الاسم |
| الوالدية | parentage_assertions, people.father_id, people.mother_id | قبول أبوة/أمومة بعد التوثيق فقط |
| المصاهرة | marriages | تاريخ كل علاقة، لا استنتاج للأبناء |
| الرعاية | care_delegations | ولاية/كفالة مختلفة عن النسب |
| الحسابات | user_profiles, auth identity | ربط بعد إثبات مستقل |
| الأدوار | role_grants وسجلات صلاحيات V7–V8 | صلاحيات بالنطاق والمدة وسبب القرار |
| المراجعات | change_requests, request_reviews | سير عمل مع فصل مقدم/معتمد |
| المصادر | sources, evidence_links | لكل ادعاء مستند وتقييم وثوق |
| التغييرات | audit_log | append-only، تتبع من/متى/لماذا |
| الأحداث | person_events | ميلاد/وفاة/زواج/طلاق وغيرها |
| الأرشيف | archive_items, archive_people | نشر بموافقة وروابط تنزيل مؤقتة |
| التكافل | welfare_funds, welfare_cases, welfare_transactions | صلاحيات ودفتر مستقلان |
| الأسر | نماذج الأسر الحالية والتاريخية V3–V4 | عضوية زمنية لا تحدد الأبوة |
| الخدمات | جداول V9 | عروض وطلبات ومسارات اعتماد |

### قواعد البيانات الحرجة
1. FK وUNIQUE على المعرفات والعلاقات التي تقتضي التفرد، مع عدم بناء UNIQUE على الاسم وحده.
2. حماية من حلقة أصل/فرع وصلة الشخص بنفسه، عبر فحص مغلق المعاملة مع قفل مناسب وتحقيق ضد التنافس.
3. عدم إعادة تعيين معرف الشخص عند الدمج؛ استخدام سجلات تحويل/دمج مدققة وبموافقة.
4. فصل الروايات/الادعاءات/المعلومات المعتمدة مع تاريخ المصدر ومستوى الثقة، وعدم طمس الخلافات التاريخية.
5. كل تعديل نسب/خصوصية/صلاحية/وثيقة يستلزم أثر تدقيق وقرار تصريح خادمي.
6. كشف السجلات العامة من view أو endpoint مخصص يقتصر على الحقول المنشورة لا `SELECT *` من `people`.
7. فهرس بحث عربي normalised + `pg_trgm` عند التحقق من توافر الامتداد، وفهرسة `parent_id`, `father_id`, `mother_id`, `unit_id`, `status`.
8. الاستعلامات عن الشجرة تبدأ من شخص معتمد وتستخدم حد عمق/عدد عقد/مهلة؛ التخزين المؤقت مرتبط بالصلاحيات وإصدار البيانات.
9. اعتماد المعاملات idempotency key لمنع تكرار الطلبات نتيجة إعادة الضغط أو انقطاع الاتصال.
10. بيانات المشاهدة العامة لا تعكس عدادات أو مسارات لأفراد مخفيين.

## 6) عقود API المقترحة (غير منفذة)
| Method | Endpoint | المهمة | الجمهور |
|---|---|---|---|
| GET | /api/v1/lineage | وحدات النسب المنشورة مع cursor | عام |
| GET | /api/v1/lineage/:id | تفاصيل وحدة ومراجعها | حسب النشر |
| GET | /api/v1/people | بحث مقيد وفق نطاق المستخدم | مرخص |
| GET | /api/v1/people/:id | بطاقة مع الحقول المسموحة | مرخص |
| GET | /api/v1/people/:id/tree | `depth` محدود، عقد وحواف موثقة | مرخص |
| GET | /api/v1/kinship?from=&to= | صلة القرابة والمسار المسموح | مرخص |
| POST | /api/v1/requests | فتح طلب مع evidence refs | عضو |
| GET | /api/v1/requests/:id | حالة طلب وفق الملكية/الدور | عضو/مراجع |
| POST | /api/v1/requests/:id/review | اعتماد أو رفض مع سبب | مراجع مصرح |
| POST | /api/v1/uploads/presign | تصريح رفع ملف محدد الحجم/النوع | مرخص |
| GET | /api/v1/audit | البحث في الأثر الإداري | مدقق |

كل endpoint: جلسة آمنة + قرار authorize(resource, action, scope) + Zod + منع كشف IDs والوجود غير المصرح + معدل طلبات + audit + استجابة أخطاء موحدة + مراقبة.
Pagination افتراضية 20 وبحد أقصى 100؛ فروع الشجرة لها حدود منفصلة يحددها الاختبار.

## 7) البحث والقرابة والتصور البياني
- شجرة `React Flow` في Client Component فقط، وتجميع/تخطيط `ELK.js` في worker إن احتاج الأداء؛ الأسماء تظهر اعتمادًا على سياسات الخصوصية.
- API يعيد slices بالطلب؛ لا تحمل كامل القبيلة إلى متصفح المستخدم.
- العقد والحواف تحمل `status` و`sourceCount` و`visibility` المسموح، وتظهر علامة «قيد المراجعة» بوضوح.
- BFS على الروابط المعتمدة (الأب والأم) لتحديد الطريق الأقصر؛ الخوارزمية لا تثبت صحة الروابط. مصاهرة/ولاية تعرض في طبقة منفصلة.
- لا تستنتج علاقات من تطابق الكنية أو اسم الفخذ؛ إتاحة «لا توجد بيانات كافية» نتيجة صحيحة.
- اختبار حالات الأعمام/الأخوال/الأشقاء وأنصاف الأشقاء/الزيجات المتعددة/أب مجهول/شخص محجوب/نسب مختلف عليه.

## 8) نظام التصميم وتجربة الاستخدام
- هوية: زمردي داكن مع ذهبي محدود، عاجي للسطوح الفاتحة؛ شعار عربي محترف؛ خطوط عربية مرخصة مهيأة للأرقام والتشكيل.
- شاشة الهاتف أولًا، header موجز، تنقل موحد، قائمة أفراد سهلة، بطاقات شجرة قابلة للتحريك، شريط بحث واضح، مؤشرات مراجعة.
- RTL كامل مع flip للأيقونات الاتجاهية، الإنجليزية LTR مستقلة دون عكس التواريخ والأرقام دلاليًا.
- WCAG 2.2 AA كهدف، تباين ألوان، تكبير 200%، تنقل keyboard، labels، مخطط شجرة له عرض نصي بديل.
- metadata وOG وsitemap وrobots للصفحات العامة فقط؛ صفحات الأشخاص الخاصة `noindex`.

## 9) الهوية والخصوصية والأمن
- استخدام Neon Auth كما هو موثق في المشروع، مع فحص جلسة على الخادم وربط المستخدم بسجل الشخص **بعد إثبات مستقل** فقط.
- لا تعتمد على middleware وحده لمنع الوصول؛ authorization داخل كل action وroute، وRLS بسياسات فعالة مثبتة بالاختبارات.
- `person_private` محمي؛ أرقام هوية، عناوين، اتصالات، قاصرون وملفات إثبات لا تظهر علنًا ولا تسجّل في logs.
- تأكيد الحدود القانونية للبيانات الشخصية ومبرر المعالجة، حق الوصول والتصحيح والاحتفاظ والحذف، موافقة النشر للصور والمعلومات الحساسة.
- الحماية: CSP، CSRF حيث يلزم، session cookies محمية، تعقيم مخرجات وعناوين الصور، rate limit، منع enumeration، التحقق من امتدادات الملفات ومحتواها، روابط signed قصيرة، فحص malware قبل اعتماد الملفات.
- تغيير أدوار/خصوصية: مراجعة إضافية، فترة صلاحية، سجل تدقيق، إنذار أمني واستعادة.
- `DATABASE_URL`, `NEON_AUTH_*`, storage keys فقط في Vercel Secrets؛ `.env.example` أسماء متغيرات دون قيم.
- الاحتياط والاستعادة: تحقق من قدرات Neon المتاحة وخطة restore مجرّبة في staging؛ لا تفترض أن نقطة الاستعادة تكفي لملفات التخزين.

## 10) الأداء والاعتمادية
- أهداف مبدئية تستلزم قياس: LCP < 2.5s على الصفحات العامة عند اتصال قياسي، CLS < 0.1، INP < 200ms.
- هدف داخلي: نتائج البحث الشائعة p95 < 500ms على بيئة staging مستقرة، والشجرة الأولى < 2s لحجم عرض مضبوط، تقاس لا تُضمن.
- `cache` للصفحات العامة المقبولة فقط؛ تجنب تداخل نتائج صلاحيات مستخدمين.
- partial rendering، dynamic imports، lazy tree expansion، cursor pagination، image optimization، حجم JS مضبوط.
- فحص ضغط باستخدام بيانات اصطناعية حتى 100 ألف شخص مع اختبارات علاقات معقّدة.
