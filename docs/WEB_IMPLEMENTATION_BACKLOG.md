# خارطة التنفيذ التفصيلية — Next.js / TypeScript

> هذه خطة عمل مستقبلية، وليست تقرير إنجاز. المستودع الحالي يحوي مخطط قاعدة البيانات والوثائق والاختبارات، ولا توجد واجهة Next.js حتى تاريخ إعداد الخطة.

## معيار التنفيذ في كل مهمة
كل مهمة PR صغير يتضمن: كود + تحقق أنواع + اختبارات + فحص صلاحيات إذا مسّت بيانات + تحديث الوثائق + صور مراجعة للجوال والكمبيوتر عند تغيير الواجهة.

## المرحلة A — الجرد والتكامل (P0)
- [ ] فحص اتصال Neon عبر بيئة آمنة دون إظهار الأسرار.
- [ ] جرد `information_schema`/pg_catalog: الجداول، المفاتيح والفهارس، سياسات RLS، triggers وviews، حالة الترحيلات وأسماء المخططات.
- [ ] مطابقة جرد الواقع مع `supabase/migrations` وتقارير `docs/DELIVERY_STATUS.md`، وتحديد source-of-truth واحد للمهاجرات الجديدة.
- [ ] تحديد Neon Auth endpoints، session validation، ومبدأ ربط الحساب بالشخص بعد تحقق.
- [ ] اختبار استعادة قاعدة وملفات في staging؛ لا عمليات حذف/تعديل جماعية على production.
**قبول:** تقرير فرق schema متكامل، وعدم وجود أسرار مطبوعة أو معروضة.

## المرحلة B — تأسيس Monorepo (P0)
- [ ] إنشاء `pnpm-workspace.yaml` و`package.json` جذر وأداة إدارة الإصدارات وlockfile.
- [ ] `apps/web` Next.js App Router + React + TypeScript strict.
- [ ] Tailwind CSS، نظام ألوان وتايبوغرافي، مكونات accessible، design tokens.
- [ ] `[locale]` عربي RTL/إنجليزي LTR، تنسيق تاريخ هجري/ميلادي عند الحاجة، i18n دون strings متفرقة.
- [ ] نماذج `server/db`, `server/auth`, `server/authorization` ومحولات repos بعد mapping الحقيقي.
- [ ] إعداد .env.example محدث و.gitignore وفحوص منع تسريب مفاتيح.
- [ ] CI: lint, typecheck, unit, build, dependency audit, secret scanning.
**قبول:** build نظيف، صفحة عامة تعمل على mobile/desktop، أسرار runtime غير مجمعة في client.

## المرحلة C — القالب العام (P0)
- [ ] Header عربي، بحث، قوائم، footer، خط عربي، صور/شعار أصلي أو مرخص.
- [ ] رئيسية ومعلومات القبيلة وتاريخها والأخبار؛ كل النصوص غير الموثقة موسومة بوضوح.
- [ ] قائمة الأفخاذ والعوائل مع filtering ومصادر النسب المنشور.
- [ ] SEO/public sitemap/robots؛ تأكيد عدم فهرسة صفحات الأعضاء.
**قبول:** وصولية واجهة، mobile-first، روابط صحيحة، لا بيانات شخصية عامة.

## المرحلة D — الحسابات والتفويض (P0)
- [ ] Sign-up/sign-in/logout/reset مع Neon Auth.
- [ ] ربط الحساب بشخص بعد إثبات، مع حالة pending ورفض التلاعب بالمعرفات.
- [ ] تنفيذ authorize(action, resource, scope) فوق جداول V7–V8 الفعلية.
- [ ] منع self-approval، فرز المسؤوليات، scopes وexpiry، صلاحيات deny-by-default.
- [ ] اختبارات سلبية لكل دور والنطاقات.
**قبول:** account A لا يستطيع قراءة/تعديل شخص أو عائلة خارج التفويض، ومراجعة RLS فعلية.

## المرحلة E — الأشخاص والشجرة (P0)
- [ ] صفحة الشخص مع تبويبات الاسم والنسب والوثائق المسموحة.
- [ ] واجهة CRUD عبر طلبات وتدقيق لا تحديث مباشر من العميل.
- [ ] API slice للجدود والأحفاد مع ceiling للعقد/العمق والوقت.
- [ ] React Flow + ELK، legend للنسب/الزواج/الرعاية، تحريك/تكبير/طي ومؤشرات حالة الدليل.
- [ ] عرض نصي بديل، دعم touch وkeyboard، اختبار بيانات 100k اصطناعية.
**قبول:** حالات الأب/الأم والأشقاء المختلطين لا تتحول إلى نسب زائف، لا كشف بيانات محجوبة.

## المرحلة F — الطلبات والمراجعات والمصادر (P0)

- [ ] طابور مراجعة وحالات submitted/in_review/needs_info/approved/rejected/cancelled.
- [ ] قرار موافقة مستقل ومعاملة واحدة + idempotency + أثر audit.
- [ ] أرشيف خاص وmetadata/versioning وروابط signed.
**قبول:** إعادة إرسال الطلب لا تكرر السجل؛ لا نشر تلقائي لمحتوى غير معتمد.

## المرحلة G — البحث والقرابة (P1)
- [ ] تطبيع عربي مع فهرس وcandidate duplicates وتصفية اعتماد وخصوصية.
- [ ] BFS مسار قرابة للأب والأم، تحذير الروابط المختلف عليها، فصل المصاهرة.
- [ ] cache مضبوط بالهوية والنطاق وإصدار السجل.
- [ ] golden fixtures لحالات القرابة العربية وسمّياتها.
**قبول:** لا تستنتج خالًا أو عمًا من زواج أم، ولا تعرض نتيجة غير مسموحة.

## المرحلة H — التراث والمجتمع (P1)
- [ ] الأخبار والمناسبات والتاريخ والأرشيف والشخصيات المعتمدة.

## المرحلة I — التكافل والتحليلات (P2)
- [ ] سجل محاسبي مستقل، صلاحيات مزدوجة، إجراءات موافقة ومطابقة.
- [ ] تكامل مدفوعات مع مزود مرخص بعد مراجعة تنظيمية؛ لا حفظ بيانات البطاقات.
- [ ] إحصائيات مجمعة لا تكشف الأقليات، وتصدير محدد النطاق.
**قبول:** دفتر حسابات قابل للتسوية، عمليات عكسية بدل حذف السجل.

## المرحلة J — جاهزية الإطلاق (P0)

- [ ] DR: backup وrestore وrollback وتوثيق incident response.

- [ ] إطلاق تدريجي للمحتوى العام ثم للأعضاء والمراجعين.
**قبول:** توقيع مدير البيانات ومسؤول الأمن والمراجع الشرعي/التاريخي وفق حوكمة الديوان، وعدم وجود حالات حرجة مفتوحة.

## تقسيم مقترح لأول 4 دفعات Pull Requests
1. `feat/web-foundation`: pnpm + Next.js + TypeScript + i18n + صفحة عامة + CI.
2. `feat/auth-boundaries`: Neon Auth server session + feature flags + permission policy with tests.
3. `feat/lineage-directory`: read-only API للبيانات المنشورة + بطاقات الوحدات وbreadcrumb.
4. `feat/lineage-tree`: graph slice API + React Flow + تمييز المعتمد عن قيد المراجعة.

## مخاطر تعتمد عليها الجدولة
| الخطر | الاحتمال | الأثر | الإجراء |
|---|---|---|---|
| اختلاف مخطط Neon عن SQL المستودع | متوسط | مرتفع | schema inventory قبل ORM |
| خلط مصادر النسب التاريخية المعتمدة بغير المعتمدة | مرتفع | مرتفع | workflow evidence/review |
| تسريب بيانات أحياء/قاصرين | متوسط | حرج | least privilege + RLS tests |
| تعقيد tree على أحجام كبيرة | مرتفع | متوسط | slice rendering + lazy loading |
| ازدواجية supabase/neon migrations | مرتفع | مرتفع | مسار ترحيلات واحد بعد الجرد |
| تعارض صلاحيات الأدوار الديناميكية | متوسط | حرج | deny first + negative security tests |

## سياسة إنجاز
- حالات المهمات: planned -> in_progress -> PR -> verified -> released.
- «منجز» فقط بعد دمج PR ونجاح اختبارات CI، و«منشور» بعد التحقق من Vercel.
- تحضير ملفات مواصفات أو إنشاء issue لا يساوي تنفيذ الميزة.
