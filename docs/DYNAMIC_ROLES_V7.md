# نظام الأدوار والصلاحيات الديناميكية — V7

## الهدف
أن يتمكن مدير مخوّل من إنشاء دور بأي اسم، مثل «مشرف المواليد» أو «مراجع النسب» أو «مسؤول وثائق فخذ»، واختيار مزايا وصلاحيات هذا الدور دون تغيير بنية قاعدة البيانات كل مرة.

## الجداول
- `permission_catalog`: قائمة عمليات معرّفة في التطبيق، مثل `person.create` و`lineage.approve`، ومستوى الحساسية.
- `custom_roles`: تعريف أي عدد من الأدوار بأسماء عربية، نطاق أقصى، انتماء قبلي اختياري، وحالة تفعيل.
- `custom_role_permissions`: سماح/منع صلاحيات لكل دور؛ المنع الصريح له الأولوية.
- `user_custom_role_assignments`: منح دور لفرد ضمن نطاق محدد (نفسه، معال، عائلة، فخذ، قبيلة، نظام) ومدة صلاحية، مع سحب المنح.
- `permission_change_requests`: طلبات تعديل الأدوار أو منحها، مع مراجعة واعتماد.
- `permission_audit_events`: أثر عمليات منح الأدوار وسحبها وتعديل الصلاحيات، وليس كلمة المرور أو رقم الهوية.

## مثال دور قابل للتخصيص
**اسم الدور:** مشرف مواليد عائلة معينة
**النطاق:** family، ويُحدد `scope_unit_id` الخاص بالعائلة
**المسموح:** `person.create`, `person.review`, `family.read`
**الممنوع:** `lineage.approve`, `roles.manage`, `welfare.approve`
**المدة:** من تاريخ الاعتماد حتى تاريخ الانتهاء أو السحب.

## قواعد التفويض الإلزامية في API (لم تُنفّذ بعد)
1. إنشاء الدور وتعديله يتطلب `roles.manage` فعليًا؛ منح الدور يتطلب `roles.assign`؛ لا يعتمد النظام على اسم الدور أو `user_metadata`.
2. منع التصعيد: المانح لا يستطيع منح صلاحية أو نطاق أوسع من صلاحياته الفعالة، ولا يستطيع تعديل دوره بما يمنحه صلاحيات جديدة.
3. المسؤول عن الأدوار لا يكون تلقائيًا صاحب السلطة على رقم الهوية أو البيانات المالية أو النسب؛ المراجعات الحرجة تتطلب موافقة مستقلة.
4. احتساب الصلاحيات: تقاطع دور فعال + عملية مصرح بها + نطاق فعلي + غرض مشروع + حماية الحقول + موافقات؛ مع `deny` صريح يتغلب على `allow`.
5. الحساب الموقوف أو المنتهي أو السحب يوقف الصلاحيات فورًا في جهة الخادم؛ عدم الاعتماد على JWT القديم وحده.
6. وحدة الأسرة التي تُمنح صلاحية عليها تشمل فروعها فقط إن كان تصريح الإدارة يذكر ذلك صراحةً وتُستخرج الفروع من شجرة مؤكدة وغير دائرية.
7. إضافة اسم صلاحية جديد في قاعدة البيانات لا يعني أن الواجهة أو الخادم ينفّذها؛ يجب إضافة معالج محمي واختبارات السماح والمنع.
8. لا تسري أدوار V1 القديمة تلقائيًا على هذا النظام. يمكن وضع جدول ترحيل بعد مراجعة أصحاب الصلاحيات.
9. دور «self» يلزم أن يكون مرتبطًا بملف صاحب الحساب، ودور «dependent» بتفويض رعاية فعّال. التفويض المنتهي أو المسحوب يجب أن يوقف المنح على مستوى الاستعلام.
10. تقارير التدقيق لا تعرض بيانات هوية أو كلمات مرور. المراجعة الحساسة تسجل الفعل والهدف والقرار.

## صفحات الإدارة المخططة
- إدارة الأدوار: إنشاء/نسخ/تعطيل/تسمية الأدوار.
- محرر الصلاحيات: مجموعات الوحدات (الأفراد، النسب، الوثائق، التكافل، الحسابات، الإدارة).
- منح دور: بحث مستخدم، اختيار النطاق، تحديد المدة، طلب الموافقة.
- اختبار الصلاحيات: «هل يستطيع المستخدم فعل كذا على سجل كذا؟»، مع سبب السماح/المنع.
- سجل تدقيق وتغييرات: تاريخ الإصدارات والأوامر الحساسة.

## الحالة
ترحيل SQL ومخطط واجهات موثق؛ لم يتم ربط Supabase أو بناء صفحات إدارة الأدوار ولا محرك التحقق التشغيلي. الجداول الجديدة RLS مغلقة افتراضيًا، ولا يجوز استخدامها على بيانات حقيقية قبل اختبار التفويض بصورة شاملة.
