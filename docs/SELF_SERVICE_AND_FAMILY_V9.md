# V9 — بوابة الفرد والخدمات والعوائل

## ما تم إضافته
المخطط يحتوي على خدمات قابلة للتكوين ونماذج مصدرة بإصدارات، وتقديم طلبات شخصية، ومهام ومراجعات جودة، ونتائج قرابة مشفرة ذات مدة محدودة، والتحقق من الوثائق، وتاريخ تغيير الفروع، وطلبات مراجعة الخصوصية، وبيانات النسخ الاحتياطي، ومساحات عائلية خاصة.

## بوابة المستخدم — هيكل الواجهة المطلوب
بطاقتي الرقمية / شجرة نسبي / عائلتي / طلباتي / وثائقي / إشعاراتي / الخصوصية / سجل نشاطي.
الجداول الأساسية موجودة مسبقًا: `person_profiles`, `membership_cards`, `people`, `person_events`, `notifications`, `document_access_logs`, `person_record_claims`, `privacy_consents`. لم يتم نسخها.
تخطيط الصفحة ليس تطبيقًا مشغلًا حتى الآن.

## لوحة العائلة
يُبنى العرض فوق `family_statistics`, `lineage_statistics`, `work_items`, `member_service_requests`, `person_names`, `verification_tasks`, `family_document_collections`, `family_timeline`.
لا تنكشف معلومات أفراد غير مصرح بها عبر الأرقام أو البحث، ولا يحصل مدير العائلة على صلاحيات الهوية تلقائيًا.

## منشئ نموذج إضافة مولود
`service_definitions` يحدد الخدمة المطلوبة، `form_templates` يصدر نسخة معتمدة،
`form_fields` يحدد نوع الحقل والطلب والإلزام، و`form_submissions` يحفظ الأجوبة مشفرة.
نموذج يمكن تكوينه: name (short_text)، birth (date)، father (person_reference)، mother (person_reference)، document (archive_reference)، note (long_text).
النموذج المنشور يجب ألا يقبل إضافة حقول أو إعادة تسمية دون إصدار نسخة جديدة؛ يجب أن يفحص خادم موثوق الإجابات، حدود الأحجام والأنواع والحقول، ثم ينشئ طلبًا مرتبطًا بـ`change_requests`.
لا تنشئ واجهة النموذج SQL أو JavaScript تعسفيًا.

## تعديل بيانات المستخدم
الطلب يربط `member_service_requests` مع `change_requests` الأصلية. لا يُحدث تعديل اسم الجد أو الأب أو الأم `people` إلا بمعاملة اعتماد ومصادر ومراجعين مخولين مستقلين.
اجعل جميع العمليات القياسية `DENY` افتراضيًا إلا بعد التحقق من هوية المستخدم، صلة السجل والقبيلة، نطاق الدور، الخصوصية، وتاريخ التفويض.

## جودة البيانات
`data_quality_suggestions` تسجل ملاحظات محتملة، لكنها لا تغيّر حقيقة النسب. المراجعة البشرية إلزامية ولا يجوز افتراض أن الذكاء الاصطناعي يثبت الأبوة أو القبيلة.

## تغيير الفروع
`lineage_structure_changes` يمثل الطلب والموافقة وتاريخ التغيير. يجب تطبيق تغيير parent/name في معاملة خادمية بعد منع الدورات والتأكد من الدليل والمراجع؛ مع إبقاء تاريخ الاسم السابق. لا ينقل الأفراد تلقائيًا بين فروع مختلفة.

## الخصوصية والتشغيل
- `shared_kinship_results`: بيانات النتيجة مشفرة، ومفتاح نطاق الصلاحيات، مع إنهاء الصلاحية وإبطال الكاش عند تحديث النسب/الموافقة.
- `backup_runs` و`restore_tests`: تسجل بيانات حالة النسخ والاستعادة فقط؛ لا تنشئ نسخ احتياطية حقيقية من تلقاء نفسها.
- `family_spaces`: العضوية في المساحة لا تمنح تلقائيًا حق الاطلاع على جميع الأفراد أو وثائقهم.
- جميع الجداول الجديدة RLS مغلقة ولا يوجد GRANT للمتصفح.

## اختبارات قبل الإنتاج
1. اختبار تدرج صلاحيات الفرد/الأب/مدير العائلة/النسابة ورفض الاطلاع عبر الأسر.
2. نموذج غير منشور لا يقبل طلبًا؛ إصدار النموذج القديم محفوظ بأجوبته.
3. فشل تغيير نسب أو فرع دون مراجعة معتمدة.
4. التحقق من أن شجرة النسب لا تظهر البيانات المحجوبة ولا تكشفها الإحصائيات.
5. عدم تكرار تشغيل الاقتراحات أو مزامنة القرابة بعد التصحيح.
6. اختبار النسخ الاحتياطي واسترجاعه في بيئة منعزلة.
7. فحص RLS على كل جدول وواجهة تخزين وثائق.
8. قياس أداء البحث والمهام عند كثرة السجلات.

الحالة: ملفات قاعدة البيانات فقط؛ لم يتم نشر تطبيق أو توصيل API أو تطبيق SQL على Supabase خاص بديوان الحازمي.
